### 2.1 两个重要的经验教训

1. **大合并提交必须 `--no-verify`**：pre-commit 钩子（lint-staged）对 ~2800 个暂存文件执行
   prettier/静态检查，耗时 20 分钟以上仍无法完成。合并提交的内容全部来自上游
   （上游 CI 已验证格式与类型），跳过钩子是安全的；合并后用 `npm install` +
   `npm run build:packages` + `npx tsc --noEmit` 兜底验证。
2. **绝不要在钩子运行中途强杀进程**：强杀会触发 lint-staged 的中断恢复，把索引与工作区
   **硬重置回提交前状态**（本次实际发生：MERGE_HEAD 丢失、工作区回到 rc4）。恢复方式：
   确认 HEAD 提交仍在 → 清理 `.git/index.lock` → 丢弃 lint-staged 残留 stash
   （`git stash list` 中的 "lint-staged automatic backup"，确认内容已被合并提交覆盖后
   `git stash drop`）→ 重新执行合并。所有内容都可从 HEAD 与 upstream/main 完整重现。

## 3. 标准合并流程（下次照此执行）

```bash
# 0) 确认工作区干净：本地改动先提交（尤其 deploy-compose.yml / package-lock.json，
#    后者上游必有更新，不提交则 merge 会被拒绝）
git status

# 1) 备份分支（幂等安全网）
git branch dev_260928.pre-merge-$(date +%y%m%d)

# 2) 抓取上游（SSH 不通时用 https 公共仓库直接抓取）
git fetch upstream
# 或： git fetch https://github.com/LibreChat-AI/LibreChat.git main:refs/remotes/upstream/main

# 3) 预览增量与规模
git log --oneline dev_260928..upstream/main | head -40
git diff --shortstat dev_260928 upstream/main
# 重点预检数据库相关目录是否被上游改动（结论写入 docs/code-update/ 对应版本目录）
git diff --stat dev_260928 upstream/main -- packages/data-schemas/src/schema/ packages/data-schemas/src/migrations/ config/

# 4) 合并（大合并用 --no-verify 跳过钩子，理由见 2.1）
git merge --no-verify --no-edit upstream/main

# 5) 冲突处理
#    .gitignore       → 双方尾部追加的段落都保留
#    package-lock.json → git checkout upstream/main -- package-lock.json（随后 npm install 对齐）
#    deploy-compose.yml → 保留本仓库定制（自定义镜像名/端口），手工并入上游结构变化
#    其它源码冲突     → 以 upstream 为准，本仓库不在源码上做定制

# 6) 完成提交
git commit --no-verify --no-edit

# 7) 验证（见第 4 节），通过后推送
git push origin dev_260928
```

## 5. 部署镜像重建与发布

本项目 API 使用自定义镜像 `librechat-dev-api:custom`（admin-panel 为 `librechat-admin-panel:custom`），
合并后需重建：

```bash
# 仓库根的 docker/ 目录即构建脚本（build.bat / build.sh / verify.sh / save.sh）
docker/build.sh            # 或 build.bat（Windows）
docker/verify.sh           # 镜像自检
docker/save.sh             # 可选：导出 tar 到 docker/（已 gitignore，勿提交）

# 发布（deploy-compose.yml 栈）
docker compose -f deploy-compose.yml up -d
```

注意：0.8.8 起 **Docker 构建在前端构建失败时会整体失败**（此前可能静默成功），
构建日志里出现前端错误必须处理而不是忽略。

发布检查单：
1. Mongo 已备份（01 文档 4.1 节命令）；
2. 若部署库创建于 v0.8.7 及更早：先执行 tenant-index 迁移（01 文档 4.2 节）；
3. 首次启动后确认无 `Index build failed` 日志，新集合 `passkeys`/`toolapprovalgrants` 已创建；
4. 通读 `UPGRADING.md` 三节（web 搜索权限 / Redis 流合并 / 租户索引），确认 `.env` 与
   `librechat.yaml` 无需调整或按需调整（`STREAM_DELTA_COALESCE_MS` 等，见 03 文档第四节）；
5. 冒烟：登录、发消息、（如启用）2FA/Passkey、定时任务、文件上传。
